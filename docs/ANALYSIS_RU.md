### Путь от файла к голограмме

1. `SchematicsView` показывает поддержанные файлы текущей папки и запускает создание размещения.
2. `PlacementManager` читает файл через `SchematicIo` в двухпоточном IO-пуле. Загрузка одного пути кэшируется; повторная загрузка может принудительно сбросить кэш.
3. Результат возвращается в главный клиентский поток. Проверка поколения загрузки не даёт устаревшему результату заменить более новую загрузку.
4. `GhostEngine.rebuild` подготавливает `PlacementVolume`: трансформации, отключённые регионы, палитру, секции 16³ и связанные данные.
5. Снимки реально прогруженных секций создаются на клиенте с бюджетом времени. В фоне `SectionVerdict` сравнивает состояния, а `SectionMesher` строит геометрию.
6. Готовые результаты принимаются с проверкой поколения и ревизии секции. GPU-буферы загружаются с ограничением количества и времени.
7. `GhostRenderer` рисует подготовленные секции, отсекая дальние и не попадающие в область видимости. Модели блочных сущностей идут отдельным путём штатного рендера.

Это снижает работу главного потока при постоянной отрисовке: меши не строятся заново каждый кадр. Изменение блоков/чанков, трансформаций, правил сравнения и моделей помечает данные для обновления. Однако фоновые потоки всё равно используют модели, цвета и представления мира Minecraft; совместимость с изменяющими их модами требует игровых проверок.

### Путь лёгкой установки

`MinecraftMixin` передаёт ввод `ToolController`. С палкой действует режим инструмента, без неё использование передаётся `EasyPlace`. Он выбирает доступную цель через `GhostRaycast`, классифицирует следующее действие и использует `PlacementSolver` для подбора клика/поворота.

`InventoryHelper` выбирает предмет. `LookLock` отправляет поворот и временно подставляет нужное направление в обработке пакетов позиции. `TickQueue` выдерживает задержки; `FollowUps` и `NoteTuner` продолжают поддержанные действия. `BreakAssist` может предварительно разрушить блок. `BlockEntityAssist` обрабатывает текст таблички и отключённые слоты сборщика. `EntityAssist` обслуживает только рамки, картины и стойки.

Клиент отправляет игровые взаимодействия, поэтому права, расстояние, защита территории, серверная проверка кликов и реальное состояние остаются определяющими.

## Проверка и смысл показателей

Сравнение основано на block state. Категории: воздух/воздух, совпало, отсутствует, лишний блок, другой блок, другое состояние и неизвестно. При мягком режиме часть изменчивых свойств нормализуется заранее в таблицу канонических ID.

Состояние рычага, задержка повторителя, режим компаратора и ряд других свойств сохраняют значение даже при мягкой проверке. Правило доверия скрытым блокам работает на внешнем сервере и только для другого типа блока, закрытого со всех сторон; это не универсальное игнорирование ошибок.

`PlacementRuntime.progress()` делит количество CORRECT на количество ненулевых блоков. Воздух и «лишние» блоки не входят в этот знаменатель. Сущности и произвольные данные блочных сущностей также не входят. Поэтому 100% совместимо с оставшимися EXTRA, неверным содержимым сундуков и отсутствующими рамками.

Общий координатный фильтр действует на все размещения. При `countVisibleOnly=true` показатели и материалы переключаются на срез. Пока фоновой пересчёт области не готов, возможен переходный показ прежних/полных значений.

Данные непрогруженных секций берутся из запомненного результата либо Voxy/VoxyMap, когда интеграция доступна. Сохранённое состояние нельзя считать текущей серверной истиной. Вкладка проверки ограничена 200 строками; алгоритм набирает кандидатов из секций, а затем сортирует их, поэтому список не является строгой глобальной выборкой всех ближайших ошибок.

## Материалы, перенос и экспорт

Материалы вычисляются из палитры схемы и числа совпавших блоков. Количество пересчитывается в предметы: двойные плиты требуют две штуки, верхняя часть двери не удваивает дверь, аналогично кровати; имеются составные варианты горшка/цветка и торта/свечи.

Запасы учитывают предметы инвентаря и вложенное содержимое контейнеров в пределах предусмотренной глубины. «Не хватает» относится к ещё не совпавшим блокам; `shortfall()` дополнительно вычитает запасы. Материалы по WRONG_STATE могут завышать закупку: исправление кликом не всегда требует нового экземпляра блока.

В хранилищах работает конечная последовательность обычных кликов. Есть проверка занятого курсора, полного инвентаря, идентификатора контейнера, лимит шагов и прекращение при закрытии. Шалкеры переносятся целиком. Точный перенос разбивает стаки, но слишком длинный план имеет переход к QUICK_MOVE.

Запасы блоков не являются полным перечнем расходников для всех действий: сущности отсутствуют, некоторые расходники доведения не перечислены отдельно. Потребность определяется исходной схемой даже при включённых заменах.

Файловый экспорт поддерживает XLSX/CSV/Markdown/JSON и пишет в `litematica-plus/materials/`. Буфер обмена использует показанные строки; файлы строятся по полному вычисленному списку. Локализация заголовков фиксируется при экспорте. Существующие тесты проверяют форматы, подсчёт, упаковку и планирование кликов; этот запуск не проверяет реальный обмен с серверным контейнером.

## Хранение и жизненный цикл

Основной конфиг имеет версию 4, миграции и нормализацию диапазонов. JSON сохраняется через временный файл и атомарное переименование, с fallback для файловых систем без атомарной операции. Предыдущий файл копируется в `.bak`.

Сессии разделяются по адресу сервера либо имени каталога одиночного мира и измерению. Сохраняются размещения, выбранная копия, боксы, слои/границы и режим инструмента. Число сохраняемых областей ограничено 512, размещений и боксов — 256 на область. При смене контекста состояние сохраняется и восстанавливается; опасные режимы инструмента сбрасываются на выделение.

Режим только чтения защищает файл сессий от записи старой версией поверх более нового формата. Для основного конфига вместо этого предусмотрено предупреждение: неизвестные поля будут отброшены при записи.

Потоки: автоматически 1–6 для мешей, два для IO, по одному для записи и превью. Число mesh-потоков настраивается до 16. При завершении клиент сохраняет сессию, завершает writer с ожиданием и закрывает ресурсы движка/рамок. Изменения поколений и токенов защищают от части запоздалых фоновых результатов.

Схемы хранятся отдельно от сессии; ссылка на перемещённый файл не восстанавливает его данные. Запись `.litematic` заменяет файл атомарно, но не создаёт для него штатную резервную копию `.bak`.

## Производительность

В реализации есть секционная обработка, постоянные GPU-буферы, очереди срочных и ближайших задач, ограничение одновременной работы, повторное использование массивов и отсечение геометрии. Базовые значения: 320 блоков дальности, 600 мкс бюджета снимков, до 24 готовых результатов за кадр. Загрузка результатов также ограничена примерно 1 мс, а число фоновых задач связано с количеством потоков.

Это разумная организация рендера больших схем, но значения бюджета не означают строгую верхнюю границу всей работы кадра. Отдельная операция может выйти за бюджет; растут расходы на объём схемы, палитры, геометрию, превью и специальные модели.

У превью есть ограниченные кэши и упрощение больших моделей. Спецблоки имеют отдельные пределы дистанции и количества за кадр, поэтому пользователь может видеть обычные блоки дальше, чем сундуки/прочие специальные модели.

Захват новой схемы — отдельный путь: полный снимок создаётся на потоке соответствующего мира перед фоновой упаковкой. Он не использует тот же пошаговый бюджет, что проверка голограммы. На большом выделении возможны остановки клиента или встроенного сервера.

Числа FPS и времени загрузки из README не перепроверялись. Для оценки нужны фиксированные схемы, аппаратные условия и измерения frame time при загрузке, движении, изменениях слоёв и повторной загрузке ресурсов.

## Найденные риски и пробелы

**Статус на 9 октября 2026 года:** пункты 1, 2, 4, 5, 6 и 7 исправлены — вставка ставит только часть внутри слоя и границ X/Z, настройки показывают реальный результат записи, материалы различают «под рукой» и «в шалкерах/эндер-сундуке» (`12+52`), прямая вставка сообщает итог после применения последней партии и учитывает ошибки записи, лёгкая установка соблюдает закрепление IPN, рендер после сбоя восстанавливается при смене мира или ресурсов. Пункт 3 оставлен: копирование секций — быстрое копирование палитр, в одиночной игре оно идёт в потоке встроенного сервера и не останавливает клиент.

Ниже указаны наблюдения по коду. Для них не проводилось отдельное воспроизведение в игровом клиенте. Приоритет отражает последствия и порядок проверки, а не подтверждённую частоту у пользователей.

### 1. Вставка не использует визуальный срез — высокий приоритет для интерфейса

В `PasteController.startPaste()` сохраняется весь `runtime.volume()`. `tickPaste()` проходит секции объёма и не проверяет `GhostEngine.layer()` или Clip. Пользователь, который показывает один этаж, может вставить всю схему, включая воздух при `ALL`.

Это подтверждённая семантика реализации, а не доказательство ошибки относительно авторского замысла. До изменения алгоритма достаточно явно показывать объём операции и предупреждение о полном размещении рядом с подтверждением. Руководство уже описывает это ограничение.

Источник: [PasteController](../src/client/java/org/lts/litematicaplus/tool/PasteController.java), методы `startPaste`, `tickPaste`; [LayersView](../src/client/java/org/lts/litematicaplus/gui/LayersView.java).

### 2. Сообщение «сохранено» не подтверждает запись на диск — средний приоритет

`LitematicaPlusConfig.save()` сразу обновляет текущую конфигурацию, ставит запись в очередь и возвращает `true`. `writePending()` при ошибке только пишет в журнал. `SettingsView.save()` показывает сообщение об успешном сохранении до получения результата IO. Если папка недоступна или диск заполнен, параметры действуют до выхода, а следующий запуск может вернуть старые.

Нужен обратный результат фоновой записи, отображаемый в интерфейсе. Автосохранение при закрытии вкладки должно иметь такой же путь обработки отказа.

Источник: [LitematicaPlusConfig](../src/client/java/org/lts/litematicaplus/LitematicaPlusConfig.java), `save`, `writePending`; [SettingsView](../src/client/java/org/lts/litematicaplus/gui/SettingsView.java), `save`, `closed`.

### 3. Большой снимок постройки может блокировать мир — средний приоритет

`SchematicCapture.capture()` на внешнем сервере вызывает `snapshot()` синхронно на клиенте; в одиночной игре — внутри задачи встроенного сервера. Весь набор секций и блочных сущностей копируется до перехода к фоновой сборке. Лимит в десятки/сотни миллионов клеток не ограничивает длительность одного снимка.

Для крупных выделений нужен пошаговый снимок с отменой и прогрессом. Фоновая упаковка уже реализована, поэтому переносить в фон без контроля доступа весь живой мир было бы неверным исправлением.

Источник: [SchematicCapture](../src/client/java/org/lts/litematicaplus/selection/SchematicCapture.java), `capture`, `snapshot`, `build`.

### 4. Запасы материалов и доступность для установки расходятся — средний приоритет

`MaterialList.countInventory()` учитывает предметы внутри шалкеров и предметы с изменёнными данными. `InventoryHelper.has()` для обычной установки проверяет 36 основных слотов, без распаковки, и по умолчанию требует пустой component patch. Поэтому панель может считать, что всё собрано, а установка отвечать отказом из-за недоступного материала.

Подсчёт запасов полезен сам по себе; интерфейсу стоит различать «всего с собой» и «доступно для установки сейчас». Дополнительные расходники доведения и сущности также требуют отдельного списка либо явной пометки о неполном учёте.

Источник: [MaterialList](../src/client/java/org/lts/litematicaplus/materials/MaterialList.java), `countInventory`, `requirements`; [InventoryHelper](../src/client/java/org/lts/litematicaplus/tool/InventoryHelper.java), `usable`, `has`; [FollowUps](../src/client/java/org/lts/litematicaplus/tool/FollowUps.java), `next`.

### 5. Результат массовой операции может выглядеть успешнее фактического — средний приоритет

При командной вставке `changed` увеличивается после отправки команды, без отдельного подтверждения её применения. При прямом пути завершение прохода и сообщение могут предшествовать выполнению последней очереди серверных операций. Ошибки отдельных прямых записей логируются, но счётчик уже сформирован раньше.

Показателю подходит название «запланировано/отправлено», а окончательному статусу — проверка реального мира. Для прямого пути стоит ждать последней отправленной задачи до сообщения о завершении. Полноценный откат в текущем коде отсутствует.

Источник: [PasteController](../src/client/java/org/lts/litematicaplus/tool/PasteController.java), `tick`, `tickPaste`, `tickDelete`, `dispatch`.

### 6. Защита IPN ограничена отдельными путями — средний приоритет для проверки интеграции

Помощник материалов учитывает `InventoryLocks` при складывании и выборе целей точного переноса. Обычный `InventoryHelper.ensure()` лёгкой установки выбирает/заменяет слот без этого API. Поэтому закрепление слота в IPN не следует описывать как защиту от всех перемещений этим модом.

Нужна игровая проверка совместного поведения и согласованная политика для выбора/перестановки предметов. Пока ограничение явно описано в руководстве.

Источник: [InventoryHelper](../src/client/java/org/lts/litematicaplus/tool/InventoryHelper.java), `ensure`; [TransferJob](../src/client/java/org/lts/litematicaplus/materials/TransferJob.java), `deposit`, `playerTarget`; [InventoryLocks](../src/client/java/org/lts/litematicaplus/compat/InventoryLocks.java).

### 7. Подтверждение ошибки рендера требует перезапуска — ограничение восстановления

`GhostRenderer` после исключения ставит статический флаг `drawFailed` или `submitFailed` и прекращает соответствующий путь рендера. В этом классе не найдено сброса флагов при смене мира или ресурсов. Такое поведение предотвращает повторение ошибки каждый кадр, но не даёт пользователю восстановить рендер простым переключением показа.

Можно добавить явную повторную инициализацию с очисткой ресурсов и ограничением повторных попыток. До этого инструкция рекомендует перезапустить клиент и исследовать журнал.

Источник: [GhostRenderer](../src/client/java/org/lts/litematicaplus/render/GhostRenderer.java), `renderAfterLevel`, `collectSubmits`.

## Сопоставление с существующим README

Основные сценарии и клавиши README соответствуют реализации. Для полной инструкции понадобились уточнения:

- Метаданные допускают Loader 0.19.3, хотя сборка использует 0.19.5. Это разные типы сведений.
- MaLiLib не требуется самому моду, но может требоваться другим модам профиля; общее требование удалить библиотеку слишком широко.
- «64 млн блоков» для удаления в коде означает 64×1024² = 67 108 864 клетки.
- Точный перенос допускает переход к целому стеку при слишком длинном плане.
- Готовность блоков не включает все сущности, NBT контейнеров и отсутствие лишних блоков.
- Сохранение сущностей при захвате ограничено одиночной игрой; лёгкая установка не является универсальным переносом NBT.
- Замены помогают ставить материал, но не переписывают исходную схему и правила проверки.
- Вставка обрабатывает полный объём, включая скрытые текущим срезом участки.

Существующий README сохранён. Подробности вынесены в отдельное руководство, чтобы не смешивать краткое описание релиза с эксплуатационными ограничениями.
